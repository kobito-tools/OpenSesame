# アプリの名乗り方

> **状態：決定（2026-10-20）**。§9 のとおりに決まり、項目は [CONTRACTS.md](CONTRACTS.md) の ④「見せ方と操作」に任意の項目として足しました。項目の正式な形は CONTRACTS.md が決め、この文書は考え方・画面での使い方・作り方の決まり（§5・§6）を書きます。
>
> 実装：共通部品 `kit.contracts.launch`（読み込み・検査・書き出し）、kobito-workspace の `scripts/check_contracts.py`、workspace の画面（§4 のうち、サイドバー・右クリック・HOME・検索・設定「アプリ」）。各アプリが名乗るのは、これからです（§8）。
>
> この文書の例に出てくる `sample` は、説明のための架空のメモのアプリです。

新しいアプリを足したときに、**決まった形で自分のことを名乗るだけで**、workspace の画面（サイドバー・HOME・検索・カレンダー・設定）とランチャーに、そのアプリが自然に並ぶようにするための設計です。

利用者の言葉：

> Python ベースのアプリは、全て同一の呼び出し口や、規格化された保管データの型で統一されるように設計したい。他のアプリを追加されても、規格化された IO を用いて、UI にも反映されるような仕組みにできると美しい。

## 1. 考え方

| 決まり | 内容 |
|---|---|
| アプリが名乗り、workspace は並べるだけ | 見せ方（アイコン・色・種類の名前）と、できる操作は、アプリが ④ 起動情報に書く。workspace のコードには、アプリごとの見せ方を書かない |
| URL は作らず、名乗られたものだけを使う | workspace とランチャーは `kobito://…` の URL を自分で組み立てない。カード（③）・受け渡しの口（④ `receive`）・操作の一覧（この文書の `actions`）にある URL だけを開く |
| v1 の約束は壊さない | 足すのは ④ の任意の項目だけ。③ カードには何も足さない。知らない項目は読む側が無視するので、古いアプリ・古い workspace もそのまま動く |
| 名乗らないアプリも並ぶ | 新しい項目が無ければ、今と同じ見せ方になる（名前の1文字目のアイコン、日本語の種類名、すべての日付をカレンダーに出す） |
| 名指ししない規則はそのまま | 各アプリは自分のことだけを名乗る。ほかのアプリの名前は書かない |
| ユーティリティアプリは埋め込まない | ランチャー・クリップボード履歴のような常駐・ユーティリティのアプリは `embed` を書かない。workspace ではサイドバーの下の「起動するだけ」のボタンになる。アイコン・色・操作（`actions`）は名乗ってよく、操作は `command` の後ろに URL を足して起動する形で開く（iframe には出さない） |

④ を選んだ理由：

- workspace もランチャーも、すでに ④ を読んでいます。新しいファイルの置き場所を増やさずに済みます。
- ④ はアプリが起動のたび（と `setup.sh` の `--write-launch-info`）に書き直すので、アプリを更新すれば名乗りも自動で新しくなります。
- ④ は PC 固有の場所にあるので、アイコンのファイルの絶対パスをそのまま書けます。

## 2. 今の規格で、アプリを足すだけで出るもの・出ないもの

2026-10-20 の `kobito_workspace/app/` と、その時点の Python のアプリ4つが実際に書き出しているものを読んで調べました。

### 2.1 出るもの

| 画面の場所 | 使っている約束 | 今の見え方 |
|---|---|---|
| サイドバーのボタン | ④ `app`・`name`・`embed` | 名前の1文字目を丸で表示。名前の順に並ぶ |
| 「起動する」だけのボタン（`embed` なし） | ④ `command` | 同上 |
| ⌘1〜9 でのアプリの切り替え | ④ | サイドバーの順 |
| iframe の表示、ダイアログ、ドロップ、通知、題名 | ④ の埋め込みの起動、⑤ | アプリによらず同じ |
| リンクを開く・表示中のアプリへ `navigate` | ②・④・⑤ | アプリによらず同じ |
| HOME（今日・期限が近い・最近の更新・件数） | ③ | 種類名（`kind`）を灰色のバッジで表示 |
| 横断検索 | ③ | アプリごとにまとめ、更新の新しい順 |
| 「送る」の送り先の一覧（送る側のアプリの画面） | ④ `receive` | 起動情報の `name` と口の `label` |
| 基準パスの候補 | ⑥ | アプリによらず同じ |

### 2.2 出ないもの・足りないもの

| 画面の場所 | 今どうなっているか | 足りない理由 |
|---|---|---|
| アプリのアイコン | 名前の1文字目だけ（「カ」「ラ」…） | アイコンを名乗る項目が無い |
| アプリの色 | 全アプリ同じ色。HOME の「アプリ別に色分け」（kobito-workspace の `docs/WORKSPACE.md` §2.2）ができない | 色を名乗る項目が無い |
| 英語の表示 | アプリ名・種類名とも日本語のまま | `name` と `kind` に英語が無い |
| 種類ごとの見せ方と並べ方 | 「メモ」「日記」「予定」「Todo」「書籍」「文書」「ファイル」がすべて同じバッジ。並び順は文字の順 | `kind` は表示用の文字列で、並べ方・アイコンを持たない |
| 日付の意味 | メモのアプリのメモは**書いた日**、書籍を管理するアプリの書籍は**登録した日**が `date` に入る。これが予定と同じ扱いで HOME の「今日」に並ぶ | ③ の `date` が「予定の日」か「記録した日」かを区別できない |
| 統合カレンダー | まだ作っていない（設計だけ） | 上の「日付の意味」が決まらないと、カレンダーに何を出すか決められない |
| アプリの操作（「新しいメモ」「Todo を足す」など） | workspace からもランチャーからも呼べない。アプリを開いて中で押すしかない | 呼べる操作の一覧を名乗る項目が無い。URL の形はアプリごとに違い、workspace は組み立ててはいけない |
| ショートカットの案内 | workspace は押されたキーを ⑤ `shortcut` で渡すだけ。何が起きるかを画面に出せない | 同上 |
| アプリの設定画面への入口 | workspace の設定には基準パスしかない | 「設定を開く」URL を名乗る項目が無い |
| 入っていないアプリの紹介 | workspace には無い | 入っていないアプリは名乗れないので、これは名乗りでは解決しない（§7） |

## 3. 起動情報④に足す項目

足すのは次の5つです。どれも任意です。正式な形は [CONTRACTS.md ④「見せ方と操作」](CONTRACTS.md#見せ方と操作)にあります。

| 項目 | 内容 |
|---|---|
| `name_en` | 英語の表示名 |
| `icon` | アイコン（画像ファイルと、無いときの1文字） |
| `color` | アプリの色（シリーズの配色の名前） |
| `kinds` | カード（③）の種類ごとの見せ方。並び順・英語名・日付の扱い |
| `actions` | 外から呼べる操作の一覧（URL と表示名） |

### 3.1 全体の例

```json
{
  "app": "sample",
  "name": "Sample",
  "command": ["/opt/homebrew/bin/uv", "run", "--project", "/Users/…/Sample", "/Users/…/Sample/launch.py"],
  "embed": ["--embedded"],
  "receive": [ … ],

  "name_en": "Sample",
  "icon": { "file": "/Users/…/Sample/assets/icon.svg", "glyph": "✎" },
  "color": "orange",
  "kinds": [
    { "kind": "メモ", "label_en": "Memo", "glyph": "✎", "dates": "record" },
    { "kind": "日記", "label_en": "Diary", "glyph": "📔", "dates": "record" }
  ],
  "actions": [
    { "id": "new", "label": "新しいメモ", "label_en": "New memo", "url": "kobito://sample/new", "role": "new", "shortcut": "cmd+n" },
    { "id": "diary-today", "label": "今日の日記", "label_en": "Today's diary", "url": "kobito://sample/diary/{today}" }
  ]
}
```

### 3.2 `name_en`

| 項目 | 必須 | 内容 |
|---|---|---|
| `name_en` | | 英語の表示名。無ければ `name` を使う |

### 3.3 `icon`

| 項目 | 必須 | 内容 |
|---|---|---|
| `file` | | アイコンの画像の絶対パス。`.svg` か `.png`、256 KB まで。正方形 |
| `glyph` | | 画像が無い・読めないときに丸の中に出す1〜2文字（絵文字でもよい） |

- どちらも無ければ、今と同じく `name` の1文字目を出します。
- workspace は画像を `/api/apps/<アプリID>/icon` で配り、`<img>` で表示します（SVG の中のスクリプトは `<img>` では動かないため）。拡張子と大きさが合わなければ使いません。
- ランチャーも同じ `file` をアイコンに使えます。
- 画像はアプリのリポジトリの中に置き、そのパスを書きます。起動のたびに書き直すので、フォルダを移しても追いつきます。

### 3.4 `color`

| 項目 | 必須 | 内容 |
|---|---|---|
| `color` | | シリーズの配色の名前。`blue`・`green`・`orange`・`red`・`purple`・`teal`・`pink`・`gray` のどれか |

- 色そのもの（`#…`）ではなく名前にするのは、ライトとナイトの両方で読みやすい色を `kobito-theme.css` がまとめて決めるためです（`--kobito-app-blue` のような変数を足す）。
- 知らない名前なら、色を付けません。
- 利用者は workspace の設定で、アプリごとに色を変えられます（`.kobito-tools/Workspace/settings.json`）。

### 3.5 `kinds`（カードの種類ごとの見せ方）

カード（③）は変えずに、そのアプリのカードの `kind` の文字列ごとに、見せ方を名乗ります。

| 項目 | 必須 | 内容 |
|---|---|---|
| `kind` | ○ | カードの `kind` と同じ文字列 |
| `label_en` | | 英語の種類名 |
| `glyph` | | バッジに添える1〜2文字 |
| `dates` | | 日付の扱い（下の表）。無ければ `"event"` |

- **配列の順が、並べる順**です。HOME の件数・検索の結果は、この順に並べます。名乗っていない種類は、その後ろに文字の順で並べます。
- 読む側は `kind` を文字列として突き合わせるだけで、意味は解釈しません（③ の決まりのまま）。

`dates` の値：

| 値 | 意味 | 統合カレンダー | HOME の「今日」 |
|---|---|---|---|
| `"event"` | `date`・`start` は**予定の日時** | 終日欄・時間欄に出す | 出す |
| `"record"` | `date`・`start` は**記録した日時**（書いた日・登録した日） | 日ごとの「記録」欄に小さく出す | 「今日の記録」として分けて出す |
| `"none"` | 日付はあっても、カレンダーには出さない | 出さない | 出さない |

- `due`（期限）と `done` は、どの値でも今までどおりに扱います。
- たとえば：予定を管理するアプリの「予定」は `event`、メモのアプリの「メモ」「日記」は `record`、書籍を管理するアプリの「書籍」「文書」は `record`（または `none`）になります。

### 3.6 `actions`（外から呼べる操作）

アプリが「外から呼んでよい」と決めた操作の一覧です。workspace とランチャーは、これを読んでボタンやコマンドとして並べます。

```json
"actions": [
  { "id": "new", "label": "新しいメモ", "label_en": "New memo", "url": "kobito://sample/new", "role": "new", "shortcut": "cmd+n" }
]
```

| 項目 | 必須 | 内容 |
|---|---|---|
| `id` | ○ | そのアプリの中で一意で、変えない名前（ランチャーはこれで覚える） |
| `label` | ○ | 表示名（日本語）。動詞で終える（「新しいメモ」「Todo を足す」） |
| `url` | ○ | ② の形の URL。**宛先は自分のアプリID**だけ。ほかのアプリIDなら、その1件を捨てる |
| `label_en` | | 英語の表示名 |
| `role` | | よく使う操作の決まった名前（下の表）。workspace が決まった場所に置く |
| `shortcut` | | 埋め込み中にこの操作を呼ぶキー（⑤ `shortcut` の `key` と同じ形、`"cmd+n"` など）。案内に出すだけで、キーの処理は今までどおりアプリが行う |

`url` の中で使える置き換え：

| 書き方 | 置き換えるもの |
|---|---|
| `{today}` | 開く側の PC の今日の日付（`YYYY-MM-DD`） |

- ほかの `{…}` を含む操作は、その1件を捨てます（`{file}` は受け渡しの口だけで使う）。
- 置き換えたあとの URL は、② と同じように開きます。

`role` の決まった名前：

| `role` | 意味 | workspace が置く場所 |
|---|---|---|
| `new` | 新しいものを作る | サイドバーのアプリのボタンを右クリックしたときの一番上、HOME の「＋」 |
| `settings` | そのアプリの設定画面を開く | workspace の設定の「アプリ」の欄に「設定を開く」 |

知らない `role` は無視して、ふつうの操作として並べます。

#### 操作の開き方

| 開く側 | 開き方 |
|---|---|
| workspace | ⑤ の `open` と同じ。宛先が埋め込めるアプリなら、その iframe に切り替えて `navigate` を送る。そうでなければ `command` の後ろに URL を足して起動する |
| ランチャー | `command` の後ろに URL を足して、シェルを通さずに起動する（④ の決まりのまま）。アプリがすでに起動していれば、アプリの2回目の起動の仕組みが受け取る |

#### ランチャーからの使い方

ランチャーのアプリが読める形を決めます。ランチャーのコードはランチャーのものなので、ここでは読む側の決まりだけを書きます。

1. ランチャーは、PC 固有領域の `kobito-tools/apps/*.json` をすべて読み、`actions` を「アプリ名 › 操作の名前」の一覧にして、キーに割り当てる候補として出します。
2. 割り当てたときは、**URL や起動コマンドではなく、アプリID と操作の `id` だけ**を覚えます（例：`{"kind": "kobito-action", "app": "sample", "action": "new"}`）。
3. キーが押されたら、その時点の起動情報を読み直し、`actions` から同じ `id` を探して開きます。アプリのフォルダを移しても、URL の形を変えても、割り当てはそのまま動きます。
4. 見つからない（アプリを消した・操作を減らした）ときは、ボタンを灰色にします。
5. アイコンは、起動情報の `icon.file` を使えます。

アプリIDはランチャーの設定の中に保存するだけで、ランチャーのコードには書きません（名指ししない規則の例外「利用者が選んだものを保存するだけ」に当たります）。

#### 名乗れる操作の例

どれも、そのアプリがすでに受け付けている URL を書きます。

| 操作 | URL |
|---|---|
| 新しいメモ（`new`） | `kobito://sample/new` |
| 今日の日記 | `kobito://sample/diary/{today}` |
| 今日を開く | `kobito://sample/day/{today}` |
| 設定を開く（`settings`） | `kobito://sample/settings` |

## 4. 名乗りを使って、workspace の画面はこう変わる

| 画面の場所 | 使う項目 | 変わること |
|---|---|---|
| サイドバー | `icon`・`color` | アイコンと色で並ぶ。名乗らないアプリは今のまま |
| サイドバーの右クリック | `actions` | そのアプリの操作が並ぶ（`role: new` が一番上） |
| HOME「今日」 | `kinds[].dates` | 予定（`event`）と「今日の記録」（`record`）を分ける。`none` は出さない |
| HOME「最近の更新」 | `color`・`kinds` | アプリの色の印と、種類の `glyph` |
| HOME「件数」・検索の結果 | `kinds` の順 | アプリが決めた順に種類を並べる |
| 統合カレンダー | `kinds[].dates`・`color` | `event` は時間欄・終日欄にアプリの色で、`record` は日ごとの記録欄に出す |
| ⌘K の検索欄 | `actions` | 入力に合う操作を、カードの検索結果の上に出す（「メモ」と打つと「Sample › 新しいメモ」） |
| ショートカットの案内 | `actions[].shortcut` | 表示中のアプリで使えるキーを、メニューと「?」の画面に出す |
| 設定「アプリ」 | `role: settings`・`color` | アプリの一覧に「設定を開く」と色の変更 |
| 英語の表示 | `name_en`・`label_en` | 言語を English にしたとき |

## 5. 同じ呼び出し口（Python のアプリが受け付ける起動の形）

シリーズの Python のアプリは、みな同じ形で起動できます。これを「シリーズの Python アプリの呼び出し口」として文書にします（約束の外の、作り方の決まり）。2026-10-21 からは、入口の名前も `launch.py` にそろえ、名乗りを出すだけの `--metadata` を足しました。入口と目印（`kobito-app.json`）の決まりは [APP_PACKAGE.md](APP_PACKAGE.md) にあり、共通部品の `kit.cli.run()` がこの引数を読みます。

| 起動の形 | すること |
|---|---|
| `<command>` | 単体のウインドウで開く（`<command>` は `uv run --project <リポジトリ> <リポジトリ>/launch.py`） |
| `<command> kobito://<アプリID>/…` | その URL を開く。起動中なら、起動中のウインドウへ渡す |
| `<command> <embed> --dataset <基準パス> --parent-origin <origin>` | workspace の中で表示する（④・⑤）。`<embed>` は `--embedded` |
| `<command> --write-launch-info` | 起動情報（④）だけを書いて終わる。`setup.sh` から呼ぶ |
| `<command> --metadata` | 名乗り（④と同じ形の JSON）を標準出力に出すだけ。何も書かない |

URL の `<アプリID>` より後ろの形はアプリが決めます（②）。ただ、新しいアプリは、次の名前を同じ意味で使うと、読みやすくなります。workspace とランチャーはこの名前に頼らず、必ず `actions`・カード・`receive` にある URL を開きます。

| URL の後ろの部分 | 意味 |
|---|---|
| （なし） | 開くだけ |
| `open/<ID>` | カードのものを開く（`?dataset=` 付き） |
| `new` | 新しいものを作る |
| `import?…&file={file}` | 受け渡しを受け取る |
| `settings` | 設定画面を開く |

## 6. 規格化された保管データ

アプリ間で読み合うデータの形は、すでに約束で決まっています。アプリの中のデータ（DB）は各アプリのものなので、約束にはしません。

| データ | 決まっている形 | 誰が読むか |
|---|---|---|
| 基準パス・共有タグ | ⓪-1・⓪-2 | 全アプリ |
| 横断表示に出すもの | ③ カード | workspace |
| 起動の仕方・受け取れるもの・見せ方・操作 | ④ 起動情報（この文書の項目を足す） | workspace・ランチャー・送る側のアプリ |
| ほかのアプリのものへの参照 | ① ファイル参照・② リンク | 参照する側だけ |
| アプリの中のデータ | 決めない（各アプリの `.kobito-tools/<App>/`） | そのアプリだけ |

アプリの中のデータも、今の Python アプリは共通部品のおかげで、次の点がそろっています。新しいアプリもこれに合わせることを勧めます（約束ではありません）。

| 点 | 今の形 |
|---|---|
| DB | SQLite（`kit.database`、DELETE モード）。`<App>/database/` に置く |
| ID | `<種類>-<UUID>`（例：`memo-…`・`item-…`）。カードの `id` にそのまま使う |
| 日時 | ISO 8601、時差付き（`kit.dataset.timestamp`） |
| 消したもの | `deleted_at` を入れて残し、カードからは消す |
| タグ | `kit.tags` の表で共有タグを写す |
| PC 固有の設定 | `kobito-tools/<App>/settings.json`（`kit.paths.Settings`） |

## 7. この仕組みで解決しないこと

| こと | 理由と扱い |
|---|---|
| 入っていないアプリの紹介 | 入っていないアプリは起動情報を書けない。紹介は GitHub の organization `kobito-tools` のプロフィールに任せる（topic `kobito-app` の付いたリポジトリの一覧）。workspace は名簿を持たない |
| 設定の項目そのものを workspace の中に並べる | 項目の形を約束にすると、アプリが変わるたびに約束が変わる。各アプリの設定画面を開く（`role: settings`）だけにする |
| workspace の中で表示しているアプリへ、ランチャーから操作を届ける | ランチャーは `command` で起動するので、単体のウインドウで開く（またはアプリの2回目の起動の仕組みが受け取る）。workspace の iframe の中に届けたい場合は、workspace が `kobito://` を受け取る仕組み（kobito-workspace の `docs/WORKSPACE.md` §4）と一緒に考える |
| Swift・Tauri のアプリ | 共通部品を使えないが、④ に同じ項目を書けば同じように並ぶ。ユーティリティのアプリなら `embed` を書かず、起動ボタンとして並ぶ |

## 8. 作るときの順番

| 順 | どこ | すること |
|---|---|---|
| 1 | kobito-workspace の文書 | 決まった項目を CONTRACTS.md の ④ に足す（任意の項目として） |
| 2 | 共通部品 `kit.contracts.launch` | `normalize` で新しい項目を確かめる（形の違う項目・1件だけを捨てる）。`write` に引数を足す。`actions(record)`（置き換え済みの URL を返す）を足す。テスト |
| 3 | 共通部品 `kobito-theme.css` | アプリの色の変数（ライト・ナイト）を足す |
| 4 | `scripts/check_contracts.py` | 新しい項目の確認を足す |
| 5 | workspace | `/api/state` に名乗りを渡す、アイコンを配る、サイドバー・HOME・検索・⌘K・設定を名乗りで作る。統合カレンダーを `dates` に合わせて作る |
| 6 | 各アプリ | 共通部品を写し直し、`write_launch_info()` で名乗る（アイコンの画像を足す） |
| 7 | ランチャー | 起動情報の `actions` を読んでキーに割り当てられるようにする |

2〜5 は workspace の中だけで進められます。6 と 7 は、アプリごと・ランチャーごとの変更として、別々に進められます。どの順で入っても、名乗っていないアプリは今のままに見えるだけで、壊れません。

## 9. 決まったこと（2026-10-20）

利用者が、9つすべてを案（おすすめ）のとおりに決めました。

| 番号 | 決めたこと | 決まった形 |
|---|---|---|
| 1 | 名乗りを置く場所 | ④ 起動情報に、任意の項目として足す |
| 2 | 色の書き方 | シリーズの配色の名前（8色）。色そのもの（`#…`）は書かない |
| 3 | アイコンの渡し方 | 画像ファイルの絶対パス（`icon.file`）＋代わりの1文字（`icon.glyph`） |
| 4 | 日付の扱いの値 | `event`・`record`・`none` の3つ。無ければ `event` |
| 5 | `role` の名前 | `new`・`settings` の2つから始める（2026-10-21 に1つ外した。[CONTRACTS.md の変更の記録](CONTRACTS.md#変更の記録)） |
| 6 | URL の置き換え | `{today}` だけ |
| 7 | ランチャーが覚えるもの | アプリIDと操作の `id` だけ |
| 8 | ランチャーから、workspace の中で表示中のアプリへ届けるか | 今は届けない（単体のウインドウで開く。§7） |
| 9 | 「同じ呼び出し口」（§5）と保管データの勧め（§6）の置き場所 | この文書に、作り方の決まりとして置く |

あわせて、ユーティリティアプリ（ランチャー・クリップボード履歴など）は workspace に埋め込まず、起動ボタンだけにすると決まりました（§1）。

## 10. 埋め込みに対応するアプリが守ること

workspace の中に表示されるアプリについての決まりです（2026-10-21 に kobito-workspace の `docs/ARCHITECTURE.md` から移しました）。共通部品がほとんどを肩代わりしますが、各アプリの画面とサーバーは次を守ります。

| 項目 | 内容 |
|---|---|
| 入口と目印 | リポジトリの直下の `launch.py` だけを入口にし、引数の形を全アプリでそろえる。直下に `kobito-app.json` を置く（[APP_PACKAGE.md](APP_PACKAGE.md)） |
| 画面とのやり取り | HTTP（JSON）だけで行う。pywebview の `js_api` に頼らない。サーバーから画面への知らせは Server-Sent Events にする |
| Cookie | 名前をアプリ固有にする（`kobito_<アプリID>_session`）。同じホストの別ポートでは Cookie が共有されるため |
| 埋め込みの許可 | `--embedded` で起動したときだけ、`frame-ancestors` に `--parent-origin` を加える。単体起動では `'none'` のまま |
| OS の機能 | ダイアログ、ファイルのドロップの実パス、通知、メニューのショートカットは、⑤ 埋め込みメッセージで workspace に頼む（`kobito-bridge.js` が吸収する） |
| 基準パス | `--dataset` で渡された基準パスを開く。埋め込み中は、画面から基準パスを切り替えさせない |

## 11. ほかのアプリとつながる機能の作り方

アプリの中で「ほかのアプリと何かをする」機能は、次の形だけで作ります。どれも、相手のアプリの名前をコードに書かずに済みます。

| したいこと | 作り方 |
|---|---|
| ファイルを参照する | ① ファイル参照。相手のアプリは関係しない |
| ほかのアプリのデータを参照する | ② リンク。利用者が workspace の検索やカードから選んだ URL を保存する（⑤ の `pick` を将来拡張して、workspace にカードを選ばせる） |
| 自分のデータを横断表示に出す | ③ カードを書き出す |
| 中身をほかのアプリへ送る | ⑦ 受け渡し。送り先の一覧は、起動情報（④）の `receive` から実行時に作る |
| ほかのアプリから中身を受け取る | 起動情報（④）に `receive` を書き、⑦ を読む |
| workspace やランチャーから操作を呼べるようにする | 起動情報（④）に `actions` を書く（自分宛ての URL だけ。`{today}` を使える） |
| workspace での見え方を決める | 起動情報（④）に `icon`・`color`・`kinds` を書く |
| 同じ基準パスの候補を出す | ⑥ 基準パスの履歴 |
